# Drifter: roadmap for remaining development

Date: 21 October 2026  
Status: proposed. T12's kit for the owner's solo round and D4's geometry check are done; nothing else is implemented or scheduled. It continues the [handling and engagement development plan](2026-10-19-drift-development-plan.md), whose engineering tasks T1–T11 are on `main` at `87c5469`. No delivery dates are committed.

## 1. Where things stand

**Web.** Circuit and Free drift keep legacy handling by default. The force model drives untimed practice, three lessons (Initiate, Sustain, Transition) and the `s-bend-2` precision challenge, scored by `precision-2`. Bests are keyed by physics, scoring, course, assistance and controls. Merging to `main` deploys to GitHub Pages.

**Still pending from the plan.** The human and hardware parts of Gates 1–4: a keyboard walkthrough, moderated sessions, human challenge attempts, and physical phones, tablets and controllers. The proposed D1–D3 Figma pages are unapproved. A [check on 21 October](2026-10-21-gate-closure.md#design-check-d2-eight-and-d3-course) found the D3 hand matches the game, but the course shape and the D2 eight's scale differ. The [decision log](2026-10-19-activities-t4-t11.md#decision-log)'s design check is answered; six tuning questions remain, each mapped to a check in the [playtest kit](2026-10-21-gate-closure.md). The FigJam diagram still needs a Figma team.

**iOS.** The native app under `ios/` is offline and two-thumb only, runs on iOS 17 or newer, and has the two courses, the same scoring and the rubber drawing. Its rigid-body car is the model the web force solver was adapted from, with [deliberate differences](2026-10-19-force-solver-t2.md#deliberate-differences-from-the-native-reference). It has no practice, lessons or challenge, keys bests by mode only, contains no network code and has no privacy manifest. It is signed under a paid organisation membership of the Apple Developer Program, but no TestFlight or App Store release is recorded.

## 2. Aim

Take Drifter from a locally verified prototype to a released game on the web and the App Store: handling proven with players, polished for people beyond friends, more to play, and a daily track with shared scores.

**Goals**

- Close the plan's human and hardware gates and make the default-handling decision from evidence.
- Release on the web and the App Store with approved designs and recorded accessibility and device performance.
- Add different cars, a best-run ghost, short medal challenges, more corner sequences and unlockable tracks.
- Bring iOS level with the web phase by phase, not in a catch-up at the end.
- Add a daily seeded track with nickname leaderboards.

**Non-goals**

- Accounts or sign-in. Leaderboards use a chosen nickname.
- One handling model shared by iOS and the web. Each platform keeps its own car and calibrates its own thresholds. This follows from choosing feature parity over shared handling; revisit it if cross-platform boards are wanted.
- Real-time multiplayer, and anything else the plan already excluded from release.

**Anti-goals.** These count as failure even if the feature works:

- Comparing or merging scores made under different physics, scoring, course, car, assistance or controls.
- Building content on handling that playtests then change, so it all needs retuning.
- A leaderboard that holds more personal data than a nickname, or fills with runs the server cannot check.
- iOS and the web drifting into different rules for the same named activity.

## 3. How the roadmap works

Phases 5–8 follow the plan's Phases 0–4. Tasks continue from T12 and design tasks from D4. Each phase has web, iOS and design work, and ends with a gate naming the evidence that closes it. A gate with missing evidence stays open; it is never passed by default.

A gate closes on a resolved outcome, not just a recorded one. _My call:_ when evidence comes back negative, such as players not retrying new content, the phase gets a fix-and-recheck loop, or the owner records why the work goes ahead anyway. If Phase 5 rejects the force model outright rather than only keeping legacy as the default, Phase 6 reworks the handling before Phase 7 builds cars and medals on it.

The plan's rules still hold: small reviewable changes, a runnable game after each task, a regression test for every fix, and a new record version for any change to physics, scoring, a course or a lesson. Playtests use both formats: a few moderated in-person sessions first, then a wider remote round.

Critical path: **Phase 5 → Gate 5 → Phase 6 → Gate 6 → Phase 7 → Gate 7 → Phase 8 → Gate 8**. One owner does this work with Claude. The roles on each task name responsibilities, not people, and a phase's tasks run one after another rather than side by side. iOS work follows the web task it ports and closes at the same gate. The owner moderates the sessions, approves the designs and scoring weights, reviews the privacy notice and handles leaderboard removals.

## 4. Phase 5 — prove the handling

**T12 — Prepare the playtest kit** · Design + engineering · Depends on: none

Status: the [playtest kit](2026-10-21-gate-closure.md) covers the owner's solo round: a task script, the measures to record and a saved results form with device, input, assistance and outcome. Every result applies to game code `87c5469`. The observer sheet for moderated sessions and a remote form for other players are still to do.

- Write the task script from the plan's [playtest record](2026-10-19-drift-development-plan.md#7-playtest-and-decision-record): make one slide, repeat it, catch excess rotation, connect opposite directions, and improve a challenge attempt after reading the result.
- Prepare an observer sheet and reuse the decision-log columns from the T4–T11 evidence. For the remote round, add a short feedback form recording device, browser, input, assistance, task outcomes and the build SHA. Collect no more personal data than the study needs.
- Pin each session to a deployed build and record its SHA and `?debug` settings.

**T13 — Run the in-person round** · Design · Depends on: T12; T15 for iOS sessions

- Moderated sessions with new and experienced drifting-game players, alternating legacy and force order.
- Cover the Gate 1 keyboard walkthrough, the Gate 2 tasks and the Gate 3 challenge attempts. Set numeric targets from the baseline observations, then freeze them before the comparison.
- Record individual observations in the decision log. A small sample supports iteration, not retention claims.
- _My call:_ with one person moderating, record each session's screen and voice with the player's consent, and write the observations up afterwards.

**T14 — Run the remote round** · Design · Depends on: T13

- Share the live build, task script and form with a wider group, including touch and controller players.
- Use it to widen device and input coverage and to check whether in-person findings recur. Treat self-reported results as weaker evidence than observed ones.

**T15 — Put the current iOS app on TestFlight** · iOS · Depends on: none

- Archive and upload the existing app under the configured team. Add the privacy manifest: the app stores settings and bests in `UserDefaults`, which Apple requires a declared reason for.
- Include it in the in-person round as its own handling, and use it for the first physical-iPhone frame-rate and touch checks.

**T16 — Measure on physical hardware** · Engineering · Depends on: T12

- Test a representative iPhone in Safari, an Android phone in Chrome, a tablet and at least one controller: reach, safe areas, audio unlock, frame rate from `?debug` timing, and controller disconnect and takeover.
- Compare with the desktop figures in the [plan-completion checks](evidence/2026-10-19-plan-completion/browser-checks.json). Fix blocking performance problems before Gate 5.

**T17 — Tune from findings and re-decide the default** · Engineering + design · Depends on: T13, T14, T16

- Answer the decision-log questions with observations: the Transition eight's loop size, the 4 s switch window, Assisted fading Sustain, challenge sensitivity, the wheelspin cue and the results band. Each change versions its lesson data or ruleset.
- Re-make the T11 decision: adopt the force model for Circuit and Free drift, or keep legacy. If adopting, follow T11's checklist: version bests, retune the title drivers, publish a change note and keep the reversible path.

**T18 — Port untimed practice to iOS** · iOS · Depends on: T15

- Add the practice activity with direct spawn, quick reset, pause, exit and overview, matching the web behaviour recorded for [T4](2026-10-19-activities-t4-t11.md).
- Add the Assisted and Reduced assistance profiles. Today's always-on countersteer becomes Assisted, and the selected profile is shown as it is on the web.
- Give iOS storage versioned record identity with the web's fields, keeping the existing mode keys so old bests survive.

**D4 — Reconcile D1–D3 with what shipped** · Design · Depends on: none

Status: checked, not yet redrawn. The D3 hand matches. The D3 course shape and zones, and the D2 eight's scale, differ from the game, and the owner chooses which side changes; see the [design check](2026-10-21-gate-closure.md#design-check-d2-eight-and-d3-course).

- Redraw the D2 eight as the shipped two 300-unit loops and check the D3 course hand against `s-bend-2`.
- Review the results band on short windows against the D3 results frames.

**Gate 5:** the human and hardware parts of plan Gates 1–4 are recorded, numeric targets are frozen, the default-handling decision is re-made from evidence, and the iOS app is on TestFlight with practice. Blocking findings are fixed or assigned to Phase 6.

## 5. Phase 6 — ready for wider release

**T19 — Fix playtest findings** · Engineering + design · Depends on: Gate 5

- Resolve blocking and major findings first, each with a regression for its root failure and checks of nearby flows.
- If a fix changes handling or scoring, re-run the affected Gate 2 or Gate 3 tasks with a few players.

**T20 — Approve and apply the designs** · Design + engineering · Depends on: D4

- Approve D1–D3 and apply the approved changes to the web.
- Adapt the screens for iOS: touch only, two thumbs, SwiftUI menus.

**T21 — Accessibility and performance pass** · Engineering · Depends on: T19, T20

- Work through the plan's presentation checks: focus, muted audio, reduced motion, text or shape as well as colour, small, tall and wide screens, and safe areas.
- Hold 60 fps on the Phase 5 phones and stay within the existing bundle budget.
- On iOS, add VoiceOver labels and Dynamic Type to menus, and honour Reduce Motion.

**T22 — Port lessons and the challenge to iOS** · iOS · Depends on: T18, T19

- Port the three lessons and the precision challenge with their evaluators and score events.
- Calibrate envelopes, durations and gate widths against the native car under both assistance profiles in the iOS tests, as the native suite already does for laps. Do not copy the web thresholds: the cars differ. Give iOS its own ruleset versions.
- Mirror the web's exploit fixtures, so a clean linked sequence beats them on iOS too.

**T23 — Release** · Product/design + engineering · Depends on: T21, T22

- Web: update the README and change note, then deploy. How and where to share it beyond friends is the owner's call.
- iOS: submit to the App Store with accurate privacy labels (no data collected), screenshots, age rating and description. The organisation's paid membership covers this, and the store lists the organisation as the seller.

**Gate 6:** blocking findings are resolved, the designs are approved, accessibility and device performance are recorded on both platforms, iOS matches the web's activities, and the web release and the App Store build are live.

## 6. Phase 7 — more to play

Every task here adds to record identity or course content, so T24 comes first.

**T24 — Extend record identity for cars and content** · Engineering · Depends on: Gate 6

- Add a car field to web and iOS record identity, defaulting to the current car so existing records keep their keys.
- Version medal and unlock state alongside bests. Never merge records with different identities.

**T25 — Different cars** · Engineering + design · Depends on: T24, D5

- Add a small set of cars with distinct tuning through `createVehicleConfig` on the web and equivalent configurations on iOS. Each car has its own bests.
- Every car must pass the existing drivability regressions (the title ghost lap, the thumb-driver lap and the lot figure of eight) and complete each lesson and the challenge under both assistance profiles.
- Cars apply to the force model only; legacy stays one car. _My call:_ legacy is the comparison baseline, and multiplying it doubles tuning work.

**T26 — Best-run ghost** · Engineering + design · Depends on: T24, D5

- Replay the stored best alongside the player, only when its record identity matches the current run.
- _My call:_ store sampled car poses rather than inputs, so the ghost does not depend on bit-identical replay. Check its size against storage limits and keep the run working when storage is unavailable.
- Make it clearly different from the title ghosts, and quiet under reduced motion.

**T27 — Short medal challenges** · Engineering + design · Depends on: T24, D5, Gate 5 targets

- Short drives with bronze, silver and gold thresholds under frozen scoring rules. Set thresholds from Phase 5 observations, then freeze them with the ruleset.
- Medals belong to a record identity, so a new car or ruleset starts fresh.

**T28 — More corner sequences and tracks** · Engineering + design · Depends on: T24, D5

- Author new precision sequences with their own course ids, exploit fixtures and recorded real-car drives, as `s-bend-2` has.
- Add tracks unlocked by score thresholds. _My call:_ unlock with medals from T27, so unlocks reward rules players can read. Existing courses stay available.
- Each new track passes the drivability regressions on both platforms.

**D5 — Car, ghost, medal and unlock screens** · Design · Depends on: Gate 6

- Car choice, ghost toggle, medal states and results, and locked and unlocked tracks, for desktop and touch, with the same accessibility checks as D1–D3.

**Gate 7:** a playtest round on the new content shows that it makes players retry, or the owner records why the phase closes anyway; every new challenge has exploit fixtures and recorded drives; each car passes the drivability suite; no records with different identities are merged; and the iOS app ships the same content as an update.

## 7. Phase 8 — daily track and leaderboards

**T29 — Spike run checking** · Engineering · Depends on: Gate 7

- A leaderboard is only as good as the server's check of a submitted run. Test whether a run recorded in Safari, Firefox and Chrome replays identically in the server runtime. JavaScript does not require `Math.sin`, `Math.atan2` and similar functions to give identical results across engines, so exact replay may fail.
- Choose from the spike between exact replay with engine-independent maths and tolerance plus plausibility checks. Record the decision before building the service.
- A replay check proves a run is physically valid, not that a person drove it. _My call:_ without accounts, scripted runs cannot be fully excluded. Rate limits per nickname and removal are the backstop, and the boards say so.

**T30 — Daily seeded track** · Engineering + design · Depends on: T28, D6

- Generate a track from a seed for each UTC day, identical on every client and on both platforms. _My call:_ one generator specified in data and implemented in TypeScript and Swift with integer seeding, so both produce the same layout.
- Validate a seed with a check that does not depend on the car (minimum radius, road width, no self-intersection). Each platform's tests also drive the upcoming seeds with its own car, and a seed is rejected if either car cannot lap it.
- Score it under a versioned ruleset. It works offline, without the leaderboard.

**T31 — Nickname leaderboard service** · Engineering · Depends on: T29, T30

- A small hosted service on a free tier, chosen in this phase. The host and the T29 check must fit free-plan limits on requests, storage and compute; if server-side replay does not fit, the check takes the cheaper path. It stores a nickname, score, record identity, day and whatever T29 needs to check the run: no accounts, emails or device identifiers.
- Add rate limits, a nickname filter, a way to remove entries, a retention period and a privacy notice. _My call:_ the notice meets New Zealand's Privacy Act 2020 at minimum.
- Separate boards by record identity. Web and iOS boards stay separate while their handling differs.

**T32 — Decide the iOS app's part** · Product/design · Depends on: T31

- The iOS app has no network code. Either keep it offline with the daily track only, since the seed needs no network, or add leaderboard submission, which changes its privacy labels. _My call until then:_ the daily track offline on iOS, with boards on the web only.

**D6 — Daily track and leaderboard screens** · Design · Depends on: Gate 7

- Daily track entry, nickname entry and editing, boards by identity, offline and unavailable states, and removal requests.

**Gate 8:** the run check rejects recorded cheat fixtures, the boards state what the check cannot catch, the privacy notice and data handling are reviewed, the service handles the expected load within free-tier limits and fails without losing the player's local result, and the iOS decision is recorded.

## 8. Decisions and risks

| Decision or risk | Where | Note |
| --- | --- | --- |
| Force or legacy default for timed courses | T17 | Decided from Phase 5 evidence only |
| Sharing the release beyond friends | T23 | Owner's call |
| Number and character of the cars | T25 | Each must pass the drivability suite on both platforms |
| Leaderboard host | T31 | Free tier only, no accounts; chosen after the T29 spike. Keep it small enough to move if a free plan's terms change |
| iOS on the leaderboards | T32 | Ends the app's offline-only design |
| Small playtest samples | Phases 5 and 7 | Evidence for iteration, not retention |
| Two codebases, one owner | Every phase | iOS work runs after its web task, so each phase takes roughly twice as long. Keep lesson data and rulesets in matching formats to limit drift |
| iOS assistance profiles | T18, T22 | Two profiles double iOS calibration |
| Cross-engine determinism | T29 | May rule out exact server replay |
| App Store review | T23 | Takes time and can reject; the organisation membership is in place |
| Storage limits | T26 | Ghost data must fit alongside bests |
