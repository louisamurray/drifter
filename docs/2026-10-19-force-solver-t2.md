# Drifter T2: isolated force-based solver

Date: 19 October 2026. Status: implemented and locally verified; not integrated into gameplay. Follows the [development plan](2026-10-19-drift-development-plan.md) and [baseline conversion contract](2026-10-19-handling-baseline.md).

## Delivered boundary

`src/game/vehicle.ts` contains an independent two-axle solver adapted from `ios/Drifter/Game/Vehicle.swift`. It imports no DOM, rendering, input-device, course, scoring or storage modules. The live web application still uses `src/game/car.ts`; its behaviour and legacy snapshots are unchanged by T2.

- All solver positions and velocities are metres and metres/second, with y up and counter-clockwise radians. `forwardSpeed` / `lateralSpeed` are explicitly body-frame velocities. Steering requests are left-positive; the existing web input needs sign conversion in T3.
- `createVehicleConfig` validates and freezes tuning once. Use it to make model variants. `STANDARD_VEHICLE` starts from the native model's mass, axle distances, tyre parameters and drivetrain constants. Custom tuning must use this factory; arbitrary objects bypass that validation.
- `createVehicleState` creates caller-owned dynamic state. `stepVehicle` mutates that state without allocating per-step state/diagnostic objects. Axle loads, slip angles, applied wheel angle, tyre forces and approximate wheelspin are exposed in the same state.
- `stepVehicle` takes explicit input, dt, model, surface and assistance. It rejects negative/non-finite or greater-than-1/60-second timesteps before mutation; dt zero is a no-op. Invalid physical state/input/surface values are rejected. Finite controls and assist demand are bounded to supported ranges.
- `NO_ASSIST` is the default. `COUNTERSTEER_ASSIST` must be passed explicitly. There is no road-query or touch heading controller inside the solver.
- Front/rear tyre curves, longitudinal load transfer, rear-wheel drive, combined traction budgets, drag, rolling resistance, a locked-rear handbrake and drift hysteresis are implemented. There is no artificial drift acceleration multiplier, explicit wheel angular-speed integration, gear model or simulated RPM.

## Deliberate differences from the native reference

1. **Wheel-frame slip:** project axle contact velocity into the steered front wheel before calculating slip; rear slip also opposes local lateral velocity in reverse. This avoids relying on forward-travel signs during backwards slides and spins.
2. **Low-speed passive forces:** cap tyre impulses using contact velocity and effective inverse mass. This prevents a single explicit tyre impulse from overshooting contact rest. Per-step energy regressions cover the combined result.
3. **Shared stopping momentum:** rear longitudinal braking uses predicted momentum after the front axle's impulse. Otherwise both axles can independently cancel the same momentum and send a nearly stopped car backwards. Six regressions reproduced that reversal before this correction; they disable rolling resistance so it cannot conceal the fault.
4. **Resistance integration:** drag and rolling resistance reduce speed without reversing momentum. Yaw damping uses an implicit update. Body velocity is rotated exactly through the yaw step, avoiding an explicit Coriolis term that can add energy.
5. **Load/telemetry ownership:** load transfer uses previous force-derived longitudinal acceleration, including resistance but excluding mere body-frame rotation. Body slip/drift state is refreshed after the step; axle-force diagnostics describe the step just applied. Positive axle loads are retained even with large requested transfer.
6. **Assistance default:** omitted assistance is actually zero. The native `DriveAssist.none` has countersteer enabled, so native-style assisted manoeuvres explicitly opt in here.

These changes are numerical/ownership decisions for the prototype, not claims of real-car accuracy. The native application source was not modified.

## Native reference capture

The checked-in [reference data](evidence/2026-10-19-native-vehicle-reference.json) was generated by compiling the actual native solver with [capture-vehicle-reference.swift](../scripts/capture-vehicle-reference.swift). This ran standalone on the host; it did not build or launch the iOS app.

- Native source SHA-256: `3aa8817b13a92b596ea3901dcd812a9c10d88bf413a2df3e64bf8f755185acf9`.
- Compiler: Apple Swift 6.4, target arm64-apple-macosx27.2.0.
- Common timestep: 1/120 second. Initial poses, physical-duration input schedules and assistance match the TypeScript comparison tests.

Recreate the capture from the repository root:

```sh
mkdir -p /private/tmp/drifter-t2-native
cp scripts/capture-vehicle-reference.swift /private/tmp/drifter-t2-native/main.swift
swiftc -module-cache-path /private/tmp/drifter-t2-native/modules ios/Drifter/Game/Vehicle.swift /private/tmp/drifter-t2-native/main.swift -o /private/tmp/drifter-t2-native/reference
/private/tmp/drifter-t2-native/reference > docs/evidence/2026-10-19-native-vehicle-reference.json
./node_modules/.bin/prettier --write docs/evidence/2026-10-19-native-vehicle-reference.json
```

## Numerical verification

The 51 tests in `src/game/vehicle.test.ts` cover:

- Immutable tuning, invalid tuning, invalid/zero dt, finite demand bounds and invalid inputs/surfaces.
- Straight acceleration, speed-dependent steering lock, stable turning, sustained slide, handbrake release, explicit assistance and a wrong correction that spins the same initial slide a countersteer correction catches.
- Deterministic replay, left/right symmetry and asphalt/grass transitions.
- Front/rear combined tyre-force limits, positive conserved vertical load, locked rear tyres, drive saturation, reduced lateral capacity under power, and zero grip without division-by-zero outputs.
- Forward and reverse coast-to-rest and two-axle brake stopping without a reversal.
- Finite outputs and no kinetic-energy increase in the tested unpowered spins/reverse slides at 60, 120 and 240 Hz, with service braking and handbrake combinations.
- Conserved world momentum and energy under force-free yaw; no false load-transfer acceleration from rotating the body frame.
- Timestep convergence on a reproducible two-second turn, plus the five native comparisons.

For the convergence fixture, position and heading error against a 960 Hz reference were:

| Solver rate | Position error | Heading error |
| --- | ---: | ---: |
| 60 Hz | 0.18318 m | 0.003216 rad |
| 120 Hz | 0.08555 m | 0.001508 rad |
| 240 Hz | 0.03668 m | 0.000648 rad |

Recommend two 120 Hz solver substeps within each existing 60 Hz web update as T3's initial integration candidate. Single 60 Hz steps pass the tested stability cases, but show larger trajectory error. Confirm input sampling, interpolation, camera and frame cost in the actual application before adopting this choice. These checks do not prove unconditional stability for arbitrary tuning, timesteps or states.

Implement the single unit/coordinate adapter, model-specific reference speed, applied-wheel-angle presentation, explicit surface/assist translation and development model selection at session boundaries.
